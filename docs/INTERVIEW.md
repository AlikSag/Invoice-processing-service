# Как показать проект на интервью

## Короткое представление

«Это учебный сервис обработки PDF-счетов на Python. Я использую Azure Document
Intelligence для извлечения данных и предоставляю два интерфейса: REST на FastAPI
и gRPC. Оба интерфейса работают с одним хранилищем заданий и планировщиком.
Пользователь отправляет документ, получает ID и отслеживает состояние обработки».

Описывай свой вклад своими словами и только в пределах того, что действительно
делал и понимаешь.

## Демонстрация на 3–5 минут

1. Покажи схему в README и объясни путь документа от загрузки до результата.
2. Запусти `uvicorn app.main:app` с настроенным `.env`.
3. Открой `http://127.0.0.1:8000/docs` и загрузи собственный тестовый PDF через
   `POST /jobs`. Используй документ без приватных данных.
4. Скопируй `req_no` и запроси статус и результат через REST.
5. Выполни `python grpc_client.py list`: тот же job виден через другой протокол.
6. Покажи `python -m pytest -q` и объясни, что проверяют пять тестов.

При отправке нескольких документов учитывай 30-секундный интервал между
запусками обработки. Если Azure недоступен, покажи код, контракт и тесты;
успешное извлечение данных без Azure не демонстрируется.

## Код, который стоит уметь объяснить

| Файл | Что разобрать |
| --- | --- |
| `app/main.py` | REST-маршруты и запуск/остановка фоновых компонентов |
| `app/uploads.py` | Общая загрузка для двух протоколов и UUID задания |
| `app/store.py` | Разрешённые переходы состояний |
| `app/scheduler.py` | Интервал запросов и запуск фонового worker |
| `app/worker.py` | Перенос синхронного SDK в поток, timeout и ошибки |
| `grpc_service/grpc_server.py` | Преобразование RPC в операции общего сервиса |
| `proto/invoice_service.proto` | Контракт сообщений и пяти RPC |

## Вопросы, к которым стоит подготовиться

- **Почему один процесс?** Хранилище — обычный словарь в памяти. Другой процесс
  получит отдельный словарь, и API перестанут видеть одни и те же задания.
- **Это распределённая очередь?** Нет. Это локальный планировщик учебного
  приложения, который обращается к внешнему облачному сервису.
- **Почему `asyncio.to_thread`?** Azure SDK синхронный; работа в отдельном потоке
  позволяет не блокировать event loop во время запроса.
- **Что ограничивает планировщик?** Время между началами запросов. Это не
  ограничение числа одновременно выполняющихся Azure-операций.
- **Что происходит при timeout?** Job получает `FAILED`. Сам SDK-вызов в потоке
  может продолжить выполнение.
- **Что проверяют тесты?** Инварианты хранилища и переходов состояний. Они не
  доказывают корректность HTTP, gRPC или реального извлечения данных в Azure.
- **Что изменится для production?** Понадобятся постоянное хранилище, очередь,
  авторизация, проверка файлов, очистка документов и наблюдаемость.

Не называй прототип production-ready и не заявляй метрики производительности,
которые не измерял. Объяснение ограничений и обоснование решений полезнее таких
заявлений.
